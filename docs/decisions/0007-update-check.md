# 0007: A daily update check that only tells you

Date: 2026-11-03. Status: accepted. Version 0.3.0.

- **What it does:** once a day the app reads `https://api.github.com/repos/juanjsebgarcia/loudstation/releases/latest`. When that release is newer, the menu shows Update Available, and its alert says how to update this copy. There are no pop-ups or notifications; the menu item disappears by itself once the running version catches up.
- **It never self-updates.** Downloading and running new code needs a signed update feed (Sparkle's EdDSA keys) and, for a downloaded app, notarisation. Both installs build from source today, so the app tells you the command instead:
  - Homebrew (the bundle lives under `Cellar/loudstation` or `opt/loudstation`): `brew update && brew upgrade loudstation && loudstation app`, with a Copy Command button. `brew update` comes first because Homebrew may otherwise go a day without fetching the tap.
  - Anything else: `make install` with the new source, which reopens the app itself.
- **What it sends:** one anonymous `GET` with `User-Agent: LoudStation/<version>`, GitHub's `Accept` header and a fixed `Accept-Language: en`, from an ephemeral `URLSession` with no cookies, cache or credentials. CFNetwork would otherwise add the user's language list, which review found when capturing the real request. `Accept-Encoding` is still added. GitHub sees the IP address and the version. The README says so, and Check for Updates Automatically turns it off; Check for Updates… still works on demand.
- **Rate limits and timing:** the unauthenticated limit is 60 requests an hour per IP, and the app makes one a day. The first check runs 45 to 90 s after launch, so a login does not start with network traffic. After that an hourly timer asks `UpdateSchedule` whether a day has passed. A last-check date more than an hour in the future (the clock was set back) counts as due. Failures are not recorded as checks, so an offline Mac retries hourly, and only the first failure in a row is logged.
- **What the answer must look like:** `parseLatestRelease` ignores drafts, pre-releases and tags that are not one to three plain numbers (`v0.3.0`, `0.3`). It also ignores any `html_url` that is not `https://github.com/juanjsebgarcia/loudstation/releases/...` on the default port with no user info. The link is only ever opened in the browser, and versions compare numerically (0.10 is newer than 0.9).
- **A new copy takes over from a stale one.** Before 0.3.0 a newly opened copy always quit if another was running.
  - **The pitfall review found:** the login item and `loudstation app` run the app through Homebrew's `opt` link. After `brew upgrade`, the old copy's bundle path still exists and already shows the new version, so the bundle on disk cannot tell old from new.
  - **The rule (`isStaleCopy`):** a running copy is stale when its program file (symlinks resolved) is missing, or was modified after that copy started, or when its bundle is an older version. The start time comes from the kernel (`sysctl` `KERN_PROC_PID`), because `NSRunningApplication.launchDate` is nil for a copy launchd started by running its executable, which is how the login item starts it. Review found this by testing a probe app.
  - **What happens:** the newcomer asks stale copies to quit, and the old copy's quit still waits for a fix in progress. Once it has asked, the newcomer waits until they have gone, with no deadline, repeating the request every 5 s and logging once if it has waited over 30 s. A deadline could leave nothing running, because both copies exit successfully and `KeepAlive` only relaunches after a failed exit.
  - **Two current copies:** the one that started first stays (`startedFirst`), so two copies opened at once never both quit.
  - **`loudstation app` uses `open -n`,** because otherwise LaunchServices only brings forward an old copy running from the same path.
  - **The `make install` route** stops the old copy with `pkill`, which does not wait for a fix; that predates this change.
- **Copies of 0.2.0 have no update check** and will not hear about 0.3.0. Their users need to be told by other means.
- **Release step this adds:** every tag needs a published GitHub release (`docs/releasing.md`), since `releases/latest` ignores bare tags. It is published last, after the tap is updated and verified, so Update Available never appears before `brew upgrade` can deliver it.
- **Tests:** version parsing and ordering, the release parser (including refused links and error answers), the newer-only rule, Homebrew detection, the staleness and tie-break rules, refused `..` paths and the schedule are unit-tested in `Tests/Unit`. The network request and the alerts are the only untested parts.
